# Подготовка заказа DriveMods после оплаты клиента

`crypto_checkout.store_adapter` реализует интерфейс `fulfillment.Store` через наблюдаемые функции настоящего магазина. Проверки выполнены через `httpx.MockTransport`; реальных входов, загрузок Device ID, платёжных документов и списаний при этой разработке не было.

## Границы готовности

- `DriveModsParseClient` — обычный клиент только для чтения и явного входа/восстановления сессии.
- `DriveModsPurchaseClient` — отдельный клиент с конкретными вызовами `licenseGetInfo`, `getUserPriceGroup`, `getUserPriceItems`, `createNewLicense`, `createPayment`, `checkStripeOrder`. Создание выключено по умолчанию: `allow_creates=False`.
- `DriveModsStoreAdapter` — привязка к настоящему `Ledger` с обязательным подтверждением зачисления Binance. `purchases_enabled=False` по умолчанию.
- `StoreJournal` — отдельная SQLite-база состояния закупки. Она содержит привязки заказов и устройств, поэтому должна храниться в защищённом каталоге данных вне Git и архива исходников. Токены, пароль, карта, Checkout client_secret и файл лицензии в неё не записываются.
- `PaymentExecutor` — интерфейс для будущего отдельно проверенного исполнения Stripe Checkout. Реализации, автоматически оплачивающей Visa, в проекте нет. Наличие сохранённой карты Link этого не заменяет.

Свойство `merchant_auth_verified` означает, что клиент успешно вошёл или проверил явно переданную сессию через `users/me`. Отдельное `merchant_device_binding_verified` изначально ложно: его может подтвердить только чтение существующего собственного оплаченного примера через `verify_existing_paid_binding(expected,source)`, включая точные устройство, комментарий заказа, позицию платежа и SHA файла. Это проверка ответа поставщика, а не включающий флаг. В живых старых примерах `deviceId/dealerComment` отсутствуют, поэтому пока эта проверка не проходит и новые `prepare/pay` блокируются **до загрузки Device ID и создания документов**. Допустимая альтернатива на будущее — отдельно подтверждённый ID записи в аутентифицированном ответе создания, связанный с исходным запросом; текущая форма такого ответа неизвестна.

`automatic_payment_ready` остаётся ложным также без настроенного исполнителя, который сам подтвердил готовность своей настоящей платёжной интеграции. Одного входа, сохранённой карты и флагов закупки недостаточно. Объявление готовности нельзя использовать как замену проверкам. Клиентскую оплату нельзя предлагать до готовности этих обязательных этапов.

## Последовательность

1. `prepare(invoice)` заново читает заказ из `Ledger`. Нужны состояния `paid/preparing` для нового заказа, точные план/стоимость/путь/SHA, TXID и запись подтверждённого зачисления Binance. Неподтверждённая, подменённая или демонстрационная оплата блокируется.
2. Исходный Device ID читается с диска с проверкой SHA-256. `licenseGetInfo` определяет устройство и доступные пакеты; устаревший или уже восстанавливаемый Device ID требует отдельного разбора. При нескольких регионах нужен явный выбор.
3. Цена проверяется по текущему собственному прайс-листу: активный товар с точными `name/spec/region`, FULL $90 или ECO $60, USD. Изменение цены блокирует создание.
4. В журнале резервируется `DMCO-<invoice_id>`, а в `dealerComment` используется точный `crypto-order:<invoice_id>`. Перед каждым созданием резерв фиксируется транзакцией SQLite.
5. Создаётся лицензия GENERATE, затем ровно один платёж на её Record ID. Результат создания не трактуется как выдуманный ID: адаптер перечитывает свои записи и находит точный маркер, затем проверяет устройство, пакет, цену, владельца и единственную позицию платежа.
6. `pay()` сначала перечитывает записи. Без проверенного исполнителя возвращается `action_required`, Checkout и списание не запускаются. При наличии исполнителя создаётся/получается Stripe Session. Требуются совпадающие ID сессии/client_secret, `amount_total` в центах и `currency=usd`, равные цене документа. Отсутствующие или изменённые поля блокируют исполнителя.
7. Исполнитель обязан до отправки оплаты сверить продавца, сумму, валюту, конкретную сессию и разрешённую Visa с окончанием 6994; лимит FULL $90/ECO $60. Его контракт поддерживает только `pending` или `action_required`, включая 3DS. Непроверенная реализация и возвращённое ею слово «paid» не подтверждают оплату.
8. `inspect()` и `download()` получают доказательство только из собственных записей магазина: оба документа активны, оплачены со статусом 3, привязаны к нужному устройству и точной сумме/позиции. Файл проверяется и хешируется; повторный скачанный файл должен иметь прежний хеш. Подтверждённый платёж и готовый файл передаются существующему Engine для доставки.

## Неопределённые результаты и перезапуск

После таймаута создания нельзя повторять его вслепую. В журнале остаётся `license_creating`, `payment_creating` или `checkout_creating`. Повторное `prepare` может только найти уже созданный документ по точному собственному маркеру и продолжить следующую стадию. Если документ не найден или найдено несколько — требуется разбор; повторного create не будет.

После запуска Checkout исполнитель вызывается не более одного раза для данного сохранённого заказа. Потеря ответа оставляет разрешёнными только чтение и сверку. Успешная поздняя оплата будет найдена чтением записей; новый Checkout или повторное списание автоматически не создаются.

Флаги создания можно отключить после подготовки: чтение и выдача уже подтверждённой лицензии остаются доступны. Новые `prepare/pay` блокируются.

## Что ещё проверить на настоящем аккаунте

Известные вызовы и поля получены из [публичного JavaScript магазина](https://store.drivemods.org/static/js/742.6075bde0bf16.chunk.js). Это внутренний интерфейс сайта, а не гарантированный внешний контракт. До включения закупок остаются конкретные проверки:

- Действительный вход и права создания нужного аккаунта; действительная форма ответов `GET_ONE/GET_LIST`, `createdBy`, `payItems`, `createdAt` и файла.
- Фактические FULL/ECO, регионы и текущие цены после `licenseGetInfo/getUserPriceItems`.
- Что сервер сохраняет точный `dealerComment` обоих документов и связь с единственным ID лицензии. `rid=RQ-UUID` не считается доказанной идемпотентностью.
- Реальные поля ответа `checkStripeOrder`: статически подтверждены `id/client_secret`; `amount_total/currency` ожидаются как поля Stripe Session, но в живом ответе ещё не проверены. Если они отсутствуют, потребуется отдельная проверенная сверка цены Checkout до оплаты.
- Настоящая реализация `PaymentExecutor` и проверка поведения Stripe/Link/3DS. Автономное списание с сохранённой Visa пока не реализовано; фиктивная успешная оплата не используется.
- Изменение статусов на 3 в обоих документах после оплаты и соответствие скачанного файла устройству. Проверка криптографической подписи лицензии не установлена по публичным ресурсам; текущая защита — собственные документы поставщика и SHA-256.

Проверки без сети:

```powershell
python -m pytest tests/test_drivemods_parse.py tests/test_drivemods_store_adapter.py -q
```

Тесты покрывают отказы до оплаты, изменение цены/устройства, потерянные ответы и перезапуск, конкурирующих обработчиков, отсутствие/повторный вызов исполнителя, неверные суммы Stripe, чужие записи и изменение файла. Все внешние запросы в них заменены `MockTransport`.
