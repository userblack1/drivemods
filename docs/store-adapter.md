# Подготовка заказа DriveMods после оплаты клиента

`crypto_checkout.store_adapter` реализует интерфейс `fulfillment.Store` через наблюдаемые функции настоящего магазина. Проверки выполнены через `httpx.MockTransport`; реальных входов, загрузок Device ID, платёжных документов и списаний при этой разработке не было.

## Границы готовности

- `DriveModsParseClient` — обычный клиент только для чтения и явного входа/восстановления сессии.
- `DriveModsPurchaseClient` — отдельный клиент с конкретными вызовами `licenseGetInfo`, `getUserPriceGroup`, `getUserPriceItems`, `createNewLicense`, `createPayment`, `checkStripeOrder`, `setPaymentIsPaying`. Создающие/изменяющие действия выключены по умолчанию: `allow_creates=False`.
- `DriveModsStoreAdapter` — привязка к настоящему `Ledger` с обязательным подтверждением зачисления Binance. `purchases_enabled=False` по умолчанию.
- `StoreJournal` — отдельная SQLite-база состояния закупки. Она содержит привязки заказов и устройств, поэтому должна храниться в защищённом каталоге данных вне Git и архива исходников. Токены, пароль, карта, Checkout client_secret и файл лицензии в неё не записываются.
- `PaymentExecutor` — интерфейс отдельно подключаемого исполнения Stripe Checkout. Сам адаптер не вводит данные карты и не управляет банковским подтверждением. Наличие сохранённой карты Link не заменяет проверку готовности исполнителя.

Свойство `merchant_auth_verified` означает, что клиент успешно вошёл или проверил явно переданную сессию через `users/me`. Историческое `merchant_device_binding_verified` подтверждает только старый строгий способ по существующему собственному оплаченному примеру с `deviceId` и комментарием; его нельзя включить настройкой. Отсутствие этих полей в старых записях не доказывает, что новая запись не сохранит переданный комментарий.

Конструктор поддерживает две явные политики:

- `binding_policy="strict"` по умолчанию: остаётся прежняя проверка поля устройства и старого собственного примера. Без неё новые `prepare/pay` блокируются.
- `binding_policy="sha256_marker", first_live_validation=True`: допускается первый оплаченный клиентом заказ без глобальной проверки старых записей. В новую лицензию и её платёж передаётся точный `crypto-order:<invoice_id>:<source_sha256>`. Отсутствующий `deviceId` допускается только при сохранении этого полного маркера **в обоих** документах, точных собственных ID/владельце/товаре/пакете/регионе/цене и единственной позиции платежа с нужным ID лицензии. Присутствующий, но другой `deviceId` всегда отклоняется. Маркер не заменяется совпадением цены, модели или версии.

`binding_policy_configured` описывает готовность выбранной политики, а `real_device_flow_verified` остаётся ложным до успешной проверки конкретного оплаченного заказа с исходником и готовым файлом. Явный режим первого живого запуска не выдаёт себя за пройденный тест и не делает историческое `merchant_device_binding_verified` истинным. Выбор политики сохраняется в журнале; старый заказ нельзя переинтерпретировать другой политикой при перезапуске.

До создания Checkout и вызова платёжного исполнителя `pay()` заново сверяет оба сохранённых маркера и все привязки. Если поставщик не сохранил или обрезал маркер, заказ останавливается до оплаты Visa; создающее действие не повторяется вслепую. Альтернатива с ID из ответа создания остаётся изолированным неподтверждённым контрактом, а не запасным разрешением выдать чужой файл.

`automatic_payment_ready` требует настроенную политику, успешный вход и отдельно готовый исполнитель Checkout. Одного входа, сохранённой карты и флагов закупки недостаточно. В рамках этой работы новый Device ID не предоставлялся, реальный сквозной запуск и списание не выполнялись.

## Последовательность

1. `prepare(invoice)` заново читает заказ из `Ledger`. Нужны состояния `paid/preparing` для нового заказа, точные план/стоимость/путь/SHA, TXID и запись подтверждённого зачисления Binance. Неподтверждённая, подменённая или демонстрационная оплата блокируется.
2. Исходный Device ID читается с диска с проверкой SHA-256. `licenseGetInfo` определяет устройство и доступные пакеты; устаревший или уже восстанавливаемый Device ID требует отдельного разбора. При нескольких регионах нужен явный выбор.
3. Цена проверяется по текущему собственному прайс-листу: активный товар с точными `name/spec/region`, FULL $90 или ECO $60, USD. Изменение цены блокирует создание.
4. В журнале резервируется `DMCO-<invoice_id>`, а в `dealerComment` используется точный `crypto-order:<invoice_id>:<source_sha256>`. Перед каждым созданием резерв фиксируется транзакцией SQLite. Хеш берётся из проверенного бинарного исходника; ID заказа и исходник заново сверяются с `Ledger`.
5. Создаётся лицензия GENERATE, затем ровно один платёж на её Record ID. Результат создания не трактуется как выдуманный ID: адаптер перечитывает свои записи и находит точный маркер, затем проверяет устройство, пакет, цену, владельца и единственную позицию платежа.
6. `pay()` сначала перечитывает записи. Без проверенного исполнителя возвращается `action_required`, Checkout и списание не запускаются. При наличии исполнителя создаётся/получается Stripe Session. Требуются совпадающие ID сессии/client_secret, `amount_total` в центах и `currency=usd`, равные цене документа. Отсутствующие или изменённые поля блокируют исполнителя.
7. Исполнитель обязан до отправки оплаты сверить продавца, сумму, валюту, конкретную сессию и разрешённую Visa с окончанием 6994; лимит FULL $90/ECO $60. Его контракт поддерживает только `pending` или `action_required`, включая 3DS. `pending` означает, что наблюдалось событие Stripe `onComplete`, а не просто открылась форма. После этого адаптер повторяет наблюдаемый завершающий шаг сайта: сохраняет фазу `notifying`, один раз вызывает `setPaymentIsPaying({id,appVersion})` для своего платёжного документа, затем сохраняет `pending`. При `action_required` уведомление не отправляется. Ни событие, ни это уведомление не устанавливают локально статус «оплачено».
8. `inspect()` и `download()` получают доказательство только из собственных записей магазина: оба документа активны, оплачены со статусом 3 и привязаны к исходнику по выбранной политике и точной сумме/позиции. В политике SHA проверяются оба полных маркера, а не наличие поля устройства в старой записи. Файл проверяется и хешируется; повторный скачанный файл должен иметь прежний хеш. Подтверждённый платёж и готовый файл передаются существующему Engine для доставки.

## Подготовка без Device ID

`await DriveModsPurchaseClient.preflight_catalog()` читает только собственные `getUserPriceGroup/getUserPriceItems`. Device ID и создание документов для этого не нужны. Живая проверка 24 ноября подтвердила два поддерживаемых сочетания: MB-S5WM ECO $60 и MB-S5WM FULL $90, оба без региона. LG-GEN5 CUSTOM+RUS $60 не переименовывается автоматически в ECO; HM-GEN5W FULL $175 не проходит лимит $90. Наличие прайс-листа не подтверждает доступность пакета конкретному устройству — это станет известно после его разрешённой проверки.

Этот метод подходит для `--check` и подготовки запуска до получения файла от владельца. Он не включает закупки и не подтверждает возможность автоматического списания Visa.

## Подготовленная корреляция ответа создания

До сетевого создания в `StoreJournal.request_proof` сохраняются точные исходный SHA-256, RID, владелец и полный снимок собственных ID лицензий с хешем снимка. Этот RID действительно передаётся в `createNewLicense`; после перезапуска новый RID вместо старого не генерируется.

`CreationReplyContract` — изолированный строгий парсер для **будущей проверенной** формы ответа создания. У него нет значения по умолчанию для пути к ID: публичный код магазина использует только `result.e`, а реального ответа создания в этой работе нет. Код вызывающей интеграции должен передать путь, установленный по реальному ответу; пример пути в тестах синтетический и не является описанием DriveMods.

Парсер отклоняет отсутствие ID, ошибки и старый ID из снимка; `CreationReplyCandidate` содержит контекст RID/владельца/SHA и хеш ответа. Это кандидат, а не подтверждение устройства, собственности или оплаты, и он не включает готовность. Для полноценного режима корреляции ещё нужны происхождение ответа от конкретного аутентифицированного запроса, чтение нового Record с проверкой владельца/типа/пакета/цены и наблюдаемая семантика возвращаемого ID. Такая корреляция могла бы связать исходник с новым Record, даже если старые `GET_ONE` не показывают `deviceId/dealerComment`. При потере ответа отсутствие ID по-прежнему запрещает догадки по цене/версии и повторное создание.

## Неопределённые результаты и перезапуск

После таймаута создания нельзя повторять его вслепую. В журнале остаётся `license_creating`, `payment_creating` или `checkout_creating`. Повторное `prepare` может только найти уже созданный документ по точному собственному маркеру и продолжить следующую стадию. Если документ не найден или найдено несколько — требуется разбор; повторного create не будет.

После запуска Checkout исполнитель вызывается не более одного раза для данного сохранённого заказа. Потеря ответа оставляет разрешёнными только чтение и сверку. Успешная поздняя оплата будет найдена чтением записей; новый Checkout или повторное списание автоматически не создаются.

То же правило действует после неопределённого ответа `setPaymentIsPaying`: фаза `notifying` фиксируется до сетевого запроса, поэтому уведомление не повторяется после таймаута или перезапуска. `inspect()` продолжает только чтение. Выдача файла разрешается после подтверждённого статуса 3 обеих собственных записей и полной сверки заказа; одного статуса «оплачивается» недостаточно.

Флаги создания можно отключить после подготовки: чтение и выдача уже подтверждённой лицензии остаются доступны. Новые `prepare/pay` блокируются.

## Что ещё проверить на настоящем аккаунте

Известные вызовы и поля получены из [публичного JavaScript магазина](https://store.drivemods.org/static/js/742.6075bde0bf16.chunk.js). Это внутренний интерфейс сайта, а не гарантированный внешний контракт. До включения закупок остаются конкретные проверки:

- Действительный вход и права создания нужного аккаунта; действительная форма ответов `GET_ONE/GET_LIST`, `createdBy`, `payItems`, `createdAt` и файла.
- Фактические FULL/ECO, регионы и текущие цены после `licenseGetInfo/getUserPriceItems`.
- Что сервер сохраняет точный `dealerComment` обоих документов и связь с единственным ID лицензии. `rid=RQ-UUID` не считается доказанной идемпотентностью.
- Реальные поля ответа `checkStripeOrder`: статически подтверждены `id/client_secret`; `amount_total/currency` ожидаются как поля Stripe Session, но в живом ответе ещё не проверены. Если они отсутствуют, потребуется отдельная проверенная сверка цены Checkout до оплаты.
- Живая проверка подключённого `PaymentExecutor` и поведения Stripe/Link/3DS с разрешённой картой. Наличие кода исполнителя само по себе не является выполненной оплатой или доказательством, что банк никогда не запросит подтверждение; фиктивная успешная оплата не используется.
- Изменение статусов на 3 в обоих документах после оплаты и соответствие скачанного файла устройству. Проверка криптографической подписи лицензии не установлена по публичным ресурсам; текущая защита — собственные документы поставщика и SHA-256.

В сохранённых собственных платёжных документах обнаружены Stripe Session с `payment_method_types=["card","link"]` и точными USD `amount_total`. Это подтверждает, что такие способы разрешались сервером, но не даёт клиенту секретный ключ продавца, off-session Customer/PaymentMethod или готовое право автоматически списать карту. Более того, `stripePayment` в уже оплаченных документах содержит старый снимок `open/unpaid`: его нельзя считать текущим состоянием сессии и тем более повторно оплачивать. Адаптер не создаёт Checkout для документа со статусом, отличным от 1.

Проверки без сети:

```powershell
python -m pytest tests/test_drivemods_parse.py tests/test_drivemods_store_adapter.py -q
```

Тесты покрывают отказы до оплаты, изменение цены/устройства, потерянные ответы и перезапуск, конкурирующих обработчиков, отсутствие/повторный вызов исполнителя, неверные суммы Stripe, чужие записи и изменение файла. Все внешние запросы в них заменены `MockTransport`.
