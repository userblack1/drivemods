# Второй ноутбук: разработка и обновление рабочего бота

Владелец 24 ноября 2026 запросил второму ноутбуку возможность редактировать и обновлять действующий бот с теми же правами, что у первого. Прежний запрет трогать сервер относился к задаче подготовки переноса; это не бессрочный запрет на последующие обновления, запрошенные владельцем.

Этот документ описывает подключение. Сам по себе он не создаёт доступ и не расширяет разрешения Codex. Выдача доступа не является основанием покупать лицензии, переводить деньги или менять другие приложения VPS.

## Три независимых доступа

1. **Codex на втором ноутбуке.** Владелец выбирает Full access в контроле разрешений под полем ввода, если этот режим доступен. Он разрешает локальные файлы/сеть и не передаёт GitHub/SSH-доступ первого компьютера. Организационные ограничения могут иметь приоритет. Документация: https://learn.chatgpt.com/docs/sandboxing.
2. **GitHub.** Репозиторий https://github.com/userblack1/drivemods остаётся публичным. Тот же userblack1 уже является владельцем; на втором ноутбуке потребуется собственный вход в GitHub/Git Credential Manager. Другому аккаунту владелец выдаёт Collaborator/write: этого достаточно для изменения кода через ветки и PR. Чужой вход в GitHub не копируется из первого Codex.
3. **Сервер.** Текущий доступ первого ноутбука — root на 89.169.7.15:22. Равный SSH-доступ означает полный контроль VPS. Вход второму ноутбуку выдаётся по его отдельному Ed25519-ключу. Пароль root и приватный ключ первого ноутбука не передаются.

## Создание ключа на втором ноутбуке

В PowerShell второго компьютера:

```powershell
$botKeyPath = Join-Path $env:USERPROFILE '.ssh\id_ed25519_drivemods'
New-Item -ItemType Directory -Force (Split-Path $botKeyPath) | Out-Null
# Если файл уже существует, используйте существующий ключ или другое имя.
ssh-keygen -t ed25519 -a 64 -f "$botKeyPath" -C "drivemods-notebook-2"
Get-Content "$botKeyPath.pub"
ssh-keygen -lf "$botKeyPath.pub"
```

Существующие ключи не перезаписывать. Passphrase при необходимости вводится самим владельцем в терминале, не в чате. Для автоматических команд можно использовать локальный SSH-agent; секреты из него не экспортируются. Передайте первому ноутбуку **только строку .pub**. Приватный файл без .pub остаётся на втором ноутбуке и не входит в Git/ZIP.

## Добавление публичного ключа владельцем

На первом ноутбуке, где уже имеется проверенный доступ к серверу, сохраните полученную публичную строку в исключённый файл `data/notebook2.pub`.

```powershell
.\.venv\Scripts\python.exe -m scripts.authorize_notebook_key --public-key-file data/notebook2.pub
.\.venv\Scripts\python.exe -m scripts.authorize_notebook_key --public-key-file data/notebook2.pub --apply
```

Первая команда — чтение и предварительная проверка. Вторая добавляет только этот ключ в существующий root authorized_keys, делает резервную копию предыдущего файла, не удаляет чужие ключи и не перезапускает SSH или бота. Требуются существующие закрытые настройки первого компьютера и Paramiko; их не публикуют и не копируют на второй ноутбук. Некорректный ключ, SSH-опции внутри строки и неподдерживаемые настройки SSH блокируют действие.

После добавления обязательно проверьте вход **со второго компьютера**:

```powershell
ssh -i "$botKeyPath" -o IdentitiesOnly=yes root@89.169.7.15 "id -u; systemctl is-active nextmod-license-bot.service"
```

Ожидается UID 0 и active. До этой проверки нельзя считать второй ноутбук подключённым. Отпечаток проверенного хост-ключа сервера Ed25519: `SHA256:wfstaqBsMPpbBx0p2BeKzOeRiy06ZmziFzCV3yliyAw`. При первом входе сверить его; при несовпадении остановиться. Проверку хоста не отключать.

## Обновление из любого ноутбука

Рабочий бот лицензий: `/opt/nextmod-license-bot`, служба `nextmod-license-bot.service`, итоговая точка входа `drivemods_bot.server_operator` с operator drop-in. Настройки `/etc/nextmod-license-bot.env`, данные `/var/lib/nextmod-license-bot/` остаются на сервере. Локально разрешён только отдельный тестовый бот; рабочий токен не используется для второго poller.

Для конкретного обновления, запрошенного владельцем:

1. Синхронизировать Git, работать в отдельной ветке, проверить diff и выполнить тесты/аудит из CONTRIBUTING. Зафиксировать конкретный SHA и получить успешный CI. Объединить готовое изменение в main согласно принятому процессу ревью.
2. Через собственный SSH-ключ проверить действующую службу, текущий код и состояние данных. Двум ноутбукам нельзя выпускать одновременно: весь выпуск выполняется под одним серверным `flock` на `/var/lock/drivemods-license-deploy.lock`; блокировка удерживается одной SSH-сессией до конца проверки/отката.
3. Подготовить отдельный каталог выпуска, сохранив старый код, конфигурацию и согласованную резервную копию SQLite/файлов заказов. Не копировать поверх `/etc` и `/var/lib` содержимое Git. Проверить зависимости и конфигурацию без запуска второго poller. Сохранить operator drop-in, тарифы, сетевые настройки и права файлов.
4. Переключить одну серверную службу на проверенную версию с короткой остановкой/перезапуском. Проверить её состояние, журнал без вывода секретов, сохранность заказов и доступность бота. При неуспехе откатить код; БД с новыми оплаченными заказами вслепую не откатывать.
5. Зафиксировать SHA, результаты и резервную копию в записи выпуска. На другом ноутбуке получить код через Git. Не редактировать файлы на сервере вне учтённого выпуска.

Автоматического развёртывания по каждому сохранению файла не настроено. GitHub workflow выполняет тесты. Обычное обновление Python-кода требует короткого перезапуска; обещать полностью непрерывную работу нельзя. При уже данном разрешении владельца на конкретное исправление с выпуском повторно спрашивать об этом же выпуске не требуется; при отсутствии такого запроса подготовка доступа сама по себе не запускает произвольное обновление.

Для отзыва доступа удалить только строку соответствующего ключа из root authorized_keys после сверки SHA256, оставив остальные ключи. Root-доступ позволяет изменять весь VPS; для другого объёма полномочий требуется отдельная роль и отдельная настройка.
