# Отдельный адрес каждому заказу

26 ноября 2026 владелец сверил первый связанный адрес в TronLink;
режим отдельного адреса подключён в существующей службе checkout.
Один адрес Binance и 99 уникальных сумм сохраняются только для старых счетов.
Удалять эту защиту, повторно
назначать старые суммы или считать присланный TXID доказательством личности
плательщика нельзя. TXID публичен.

Подготовлен `ReceivingWallet`: из публичного account xpub TRON BIP44
`m/44'/195'/0'` выводит внешние адреса `0/index`. Приватные ключи и подпись
не нужны. Ledger закрепляет адрес и счёт в одной SQLite-транзакции;
повторные запросы возвращают прежний счёт, рестарт продолжает индекс.
Адреса не переиспользуются даже после просрочки. Суммы могут быть ровно
100/70 USDT. Пространство публичной ветки — до 2^31 индексов; это не
математически бесконечное число. Индекс 0 зарезервирован владельцу.

Новая стратегия подключена в коде CheckoutService/application, но в чистой
установке выключена. Для её включения обязательны два защищённых файла: публичная
конфигурация и подтверждение владельцем первого связанного адреса в TronLink.
Действующий сервер не переключается при наличии только публичной конфигурации.

## Разовая подготовка владельцем

1. Создать собственный HD-кошелёк TRON в TronLink, скачав приложение через
   официальный сайт. Стандартный путь TronLink совпадает с подготовленным
   генератором: `m/44'/195'/0'/0/index`.
   Binance Exchange не выдаёт приватный ключ к своему депозитному адресу:
   этот адрес нельзя превратить в собственную HD-ветку.
2. Сохранить резервную фразу вне чата/сервера/репозитория. Проверить
   восстановление в доверенном приложении, прежде чем принимать деньги.
3. Экспортировать публичный account xpub в доверенной локальной среде.
   Если приложение не поддерживает такой экспорт, подготовлен локальный
   `scripts/export_tron_watch.py`: он принимает фразу только через скрытый
   интерактивный ввод и сверяет первый адрес с адресом в приложении.
   Запуск этого инструмента — действие владельца; автоматического чтения
   seed из файлов/буфера или передачи на VPS нет. Применять только после
   проверки кода и доверия локальной машине. BIP39 passphrase отличается
   от PIN/пароля приложения. Несовпадение пути/первого адреса запрещает экспорт.
4. Проверить, что владелец может получить доступ и вывести токены с адреса
   индекса 1, а не только с первого адреса. Не все приложения показывают
   произвольные производные адреса; такой кошелёк нельзя включать до проверки.
5. Передать боту только public configuration через защищённый локальный файл.
   xpub не даёт тратить средства, но раскрывает связь адресов и не должен
   публиковаться в GitHub. Seed/приватные ключи остаются у владельца.

## Условия включения

Настройки CRYPTO_RECEIVING_WALLET_FILE и CRYPTO_WALLET_VERIFICATION_FILE
задаются одновременно. В systemd доступны необязательные aliases credentials
receiving-wallet.json и wallet-verification.json. Проверка не создаёт заказов.
Подтверждение имеет строго поля fingerprint, first_address, first_child_address,
owner_confirmed=true. Значения сверяются с xpub и индексами 0/1. Это запись
фактической проверки владельцем, а не заменитель подтверждения перевода.

Новые счета с отдельным адресом получают payment_policy=tron_wallet и
wallet_fingerprint. Только подтверждённый USDT Transfer нужного контракта на
этот адрес, в срок счёта, с точной суммой и уникальным txid/log_index делает
их оплаченными. Старые строки получают payment_policy=binance при миграции
и по-прежнему требуют отдельного подтверждения Binance. Глобальная политика
существующей базы require_exchange_credit не меняется. Старые суммы и
адреса не освобождаются и не передаются другим клиентам. Стартовые сообщения
и текст счёта показывают правила выбранной стратегии/конкретного заказа.

Для переключения сохраняются копии базы и кода, устанавливаются optional
зависимости requirements.wallet.lock и два credentials. Перезапускается только
существующая служба checkout, без запуска второго poller; при незавершённой
проверке владельца новые credentials не подключаются.

Вывод/сбор средств с адресов в Binance — отдельная операция. Она не
реализована этим модулем и требует сетевых ресурсов TRON, активации адресов
при необходимости и комиссий. Нельзя обещать их отсутствие или запускать
автоматические переводы, имея лишь публичный xpub. Закупка Visa независима
от такого сбора, но на ней должен оставаться достаточный долларовый остаток.

Источники: [TRON accounts](https://developers.tron.network/docs/account),
[TronLink HD paths](https://support.tronlink.org/hc/en-us/articles/18779153013913-Learn-about-HD-wallets),
[bip_utils BIP44 public derivation](https://github.com/ebellocchia/bip_utils/blob/master/readme/bip44.md).

## Чтение блокчейна и ограничения провайдера

TronGrid-ключ хранится вне Git в защищённом env. Разрешены только
getTrc20TransactionsByAccount, walletsolidity_getNowBlock и
walletsolidity_getTransactionInfoById. Ключ не даёт права подписывать переводы.
TronReader сериализует запросы всех заказов с интервалом не менее 1,1 секунды.
Пагинация проходит через тот же ограничитель. После HTTP 429/403 новые
сетевые запросы прекращаются на Retry-After/указанный срок блокировки
с запасом, затем обычная проверка возобновляется. Частичная история не
признаётся полной, неоплаченные счета остаются неоплаченными.

В проверенном Basic-плане аккаунта квота общая для всех ключей: 500 кредитов
в секунду и 3 млн в день. Запрос истории стоит 200, два используемых метода
Solidity — по 80. При росте числа ожидающих счетов нужны оценка суточной
нагрузки и подходящая квота; отдельные адреса снимают лимит 99 счетов,
но не ограничения внешнего сервиса. Источник: [TronGrid API credit costs](https://www.trongrid.io/creditCosts).

Полный новый клиентский заказ с реальным Device ID и оплатой пока не
завершён. Флаг real_device_flow_tested остаётся false; технические проверки
и синтетические заказы не заменяют эту проверку. Банк может запросить 3DS.
