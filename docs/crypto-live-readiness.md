Этот документ отделяет проверенную работу с настоящими сервисами от тестов с имитацией внешних ответов. Переключение действующих ботов здесь не выполнялось.

## Добавлено в код

`CheckoutService` принимает исходный файл локально, сохраняет его SHA и владельца, выдаёт отдельный счёт только при готовности всего конвейера. Повтор одного действия возвращает исходный счёт. Максимум ожидающих счетов одного клиента проверяется атомарно в SQLite.

`Ledger` разделяет клиентов, пакеты, исходные файлы, суммы и транзакции. Один блокчейн-перевод или депозит Binance не может оплатить два заказа. На текущем общем адресе есть строгий предел 99 никогда не повторяющихся сумм на пакет. После исчерпания счёт не выдаётся. Повторное использование старых сумм ради увеличения лимита запрещено: поздний перевод можно ошибочно отнести другому клиенту. Для постоянного роста нужен провайдер с уникальными адресами/идентификаторами платежей.

`RuntimeWorker` независимо проверяет поступления и выполняет обработку заказов. Проверки сети ограниченно параллельные; операции поставщика последовательные; доставка не ждёт чужую закупку. Межпроцессная блокировка и журнал предохраняют от повторного списания после сбоя. Каждый выходной файл находится в каталоге своего заказа, даже если исходный файл был общим.

`DriveModsStoreAdapter` содержит сериализацию наблюдаемых запросов и журнал перед созданием лицензии/платежа. Реальные внешние записи этим адаптером пока не создавались. Его сетевые операции создания и исполнения Visa блокируются без подтверждённой готовности. Все проверки сквозного исполнения поставщика пока используют явные имитации внешних ответов.

## Что пока мешает включению без оператора

1. **Привязка устройства в настоящем ответе магазина.** Три собственные записи `GET_ONE` не возвращают `deviceId`, `dealerComment` и `region`. Двоичный файл — непрозрачные 4096 байт в Base64 без завершающего padding. Его SHA не доказывает соответствие исходному Device ID. Нельзя выдавать старую лицензию по совпадению цены, модели или версии. Требуется проверить коррелированный ID в ответе создания для одного разрешённого настоящего заказа либо получить у поставщика поддерживаемую проверку устройства. Неопределённый ответ создания нельзя повторять вслепую.
2. **Исполнение Visa.** Реального проверенного `PaymentExecutor` нет. Сохранённая Visa в Link не является серверным разрешением повторных списаний. Checkout Session только открывает оплату; статус «оплачивается» не равен «оплачено». Код не должен объявлять `automatic_payment_ready=True` через ручной флаг. Банковская аутентификация остаётся `action_required`, если её запросит Stripe/банк.
3. **Текущая неоплаченная лицензия.** Её погашение — отдельный существующий заказ, не новый подтверждённый криптоплатёж ученика. Владелец разрешил оплатить его Visa 6994 в пределах $90; до подтверждённой оплаты он остаётся неоплаченным. Платёжная запись и открытая форма не подтверждают списание.
4. **Доступность поставщика ночью.** В публичном клиенте есть модель постоплаты (`prepayCnt`, «Оплат лицензий до постоплаты»); настоящий профиль возвращает `prepayCnt=0`. Это не подтверждает предоплаченный баланс или право автоматически выдавать неоплаченные файлы. Постоплата либо автоматическое списание должны быть согласованы с DriveMods. Внутренний пополняемый кошелёк не найден.
5. **Настоящий сквозной заказ.** Нужен собственный валидный Device ID и подтверждённое поступление по отдельному тестовому заказу после готовности закупки. Чтение истории, имитации и прежняя ручная оплата не заменяют эту проверку.

Текущая производственная версия обоих ботов лицензий остаётся операторской. Криптовалютные счета в ней не включались; новые списания Visa на момент проверки не выполнялись. Полный локальный набор: 673 теста прошли. Проверки параллельных заказов и сквозной работы Store используют имитации внешних ответов; настоящий сквозной клиентский заказ не завершён. Условия Telegram для цифровых товаров описаны в [алгоритме](crypto-checkout-algorithm.md); отдельный модуль Telegram не означает разрешение включить криптооплату цифровых товаров внутри Telegram.

## Продолжение

Не сбрасывать Ledger/StoreJournal, не удалять рабочий lock-файл и не создавать повторную оплату после таймаута. Сначала завершить проверку настоящего связывания устройства и платёжного исполнителя. Затем сохранить согласованную резервную копию действующей БД и кода, подготовить отдельный выпуск, проверить readiness, выполнить один разрешённый настоящий заказ и только после этого переключать один действующий poller. Вторую копию с тем же токеном не запускать.
