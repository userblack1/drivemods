# Подготовленная сборка криптооплаты

`crypto_checkout.application` собирает отдельное приложение из настоящих
клиентов TRON, Binance, DriveMods, Telegram, Ledger, StoreJournal и worker.
Модуль не подменяет внешние сервисы имитациями и не запускается при импорте.
Действующая операторская служба продолжает работать отдельно.

Подготовлен отдельный исполнитель `BrowserStripeExecutor`: он использует
защищённое хранилище карты владельца и реальный браузер Stripe. Сохранённая
карта в Link сама по себе его не подключает. Без установленных защищённых
файлов, браузера и разрешённых настроек CLI возвращает `ready: false` и не
выставляет клиентские счета. Подключение кода не доказывает успешную покупку
настоящей лицензии: этот признак указывается отдельно.

## Проверка без Device ID и новых списаний

```sh
python -m crypto_checkout.application --check
```

По умолчанию используются только переменные процесса. Для отдельного
защищённого файла можно явно добавить `--env-file /защищённый/путь.env`.
Не передавайте значения ключей в аргументах командной строки. Список имён
переменных есть в `deploy/crypto-checkout.env.example`; в нём все значения
пустые. Старые `BOT_TOKEN`, `DATA_DIR`, `STORE_UPLOADS_ENABLED` и
`STORE_PURCHASES_ENABLED` намеренно не управляют новым приложением.

Проверка выполняет только:

- чтение высоты подтверждённой сети TRON;
- проверку прав ключа и ограниченную историю депозитов Binance;
- восстановление явно сохранённой сессии DriveMods через `users/me`;
- чтение группы цен и каталога без `licenseGetInfo` и Device ID;
- `getMe` для проверки нужного Telegram-бота.

Она не создаёт папку данных, Ledger, StoreJournal, загрузки, Device ID,
лицензии, платёжные документы или checkout. Сообщения в Telegram и
`getUpdates` не вызываются. В отчёте доступны только признаки готовности,
имена отсутствующих проверок и безопасные категории ошибок. Ключи,
содержимое ответов, идентификаторы транзакций и данные сессии не выводятся.
Возврат `0` означает полную проверенную готовность, `2` — незавершённые
условия или конфигурацию, `1` — другую безопасно описанную ошибку.

Обычный `--check` также не запускает браузер и не создаёт браузерный профиль.
Если владелец уже подключил защищённое хранилище карты, проверка кратковременно
расшифровывает его в памяти, проверяет данные и ожидаемые последние четыре
цифры, затем очищает объект. Данные карты не передаются по сети и не выводятся.
Для явно запрошенной проверки установленного браузера предусмотрена команда:

```sh
python -m crypto_checkout.application --check --probe-browser
```

Она открывает пустой временный браузер без перехода на оплату и сообщает
`browser_runtime_probed`. Финансовые записи, карточный журнал и клиентские
заказы не создаются; данные карты в браузер не вводятся. При `--run` такая проверка
браузера обязательна. `--probe-browser` нельзя сочетать с `--run` отдельно.
До подключения карты этот явный probe также работает отдельно по
`CRYPTO_BROWSER_EXECUTABLE`. Он подтверждает только запуск браузера:
`browser_runtime_verified=true` не включает `automatic_payment_ready` и не
разрешает принимать клиентские счета без остальных обязательных условий.

Без уже имеющегося примера точной привязки устройства
`merchant_device_binding_verified` остаётся `false`. Это ожидаемое состояние
при подготовке без Device ID. По умолчанию политика `strict` требует такой
проверки. Для первой настоящей проверки предусмотрена явно разрешаемая
политика `sha256_marker`, описанная ниже; прежний признак от неё не меняется.
Никакой новый файл не генерируется для обхода проверки, и контрольное
списание не требуется для подготовки кода.
Наличие в каталоге цен FULL $90/ECO $60 подтверждает только базовые цены;
совместимость конкретного устройства оно не доказывает.

## Настройки и защищённые данные

- `CRYPTO_BOT_TOKEN` — токен целевого бота. По умолчанию ожидаются ID
  `9258163194` и username `DriveMods_licensebot`; другие ожидаемые значения
  задаются явно через `CRYPTO_EXPECTED_BOT_ID` и
  `CRYPTO_EXPECTED_BOT_USERNAME`.
- `CRYPTO_RECEIVING_ADDRESS` — проверенный адрес USDT TRC20.
  `CRYPTO_NETWORK` допускает только TRON/TRC20/TRX.
- `BINANCE_READ_API_KEY` и `BINANCE_READ_API_SECRET` — отдельный ключ только
  для чтения, ограниченный IP сервера. `TRONGRID_API_KEY` необязателен.
- `CRYPTO_STORE_SESSION_FILE` — защищённый JSON ровно с полями
  `username`, `user_id`, `session_token`. Пароль не сохраняется.
- `CRYPTO_DATA_DIR` — новая отдельная папка. По умолчанию используется
  `data/crypto-checkout/application`; при размещении службы —
  `/var/lib/drivemods-checkout`. Рабочие папки прежних ботов и наблюдателей,
  обычный `data/` и папки с чужими базами отклоняются.
- `CRYPTO_STORE_REGION` — необязательный регион, если его требует
  конкретное предложение DriveMods.
- `CRYPTO_CARD_VAULT_FILE` и `CRYPTO_CARD_KEY_FILE` — два отдельных защищённых
  файла шифрованной карты владельца и ключа. В `.env` записываются только
  пути. Номер карты, срок, CVC, пароли и коды в `.env` не размещаются.
- `CRYPTO_STRIPE_PUBLISHABLE_KEY` — проверенный публичный ключ `pk_live_…`
  соответствующего Stripe-магазина; секретный `sk_live_…` не принимается.
- `CRYPTO_BROWSER_EXECUTABLE` — путь к установленному браузеру, доступному
  пользователю новой службы. Дополнительные зависимости устанавливаются
  из подготовленного `requirements.checkout.lock`.

Хранилище карты подключается только после разрешения владельца через локальную
защищённую форму. Его содержимое и ключ не включаются в Git, ZIP, вывод команд
или Telegram. Результат `owner_card_vault_configured` сообщает только о наличии
конфигурации. Требование банка подтвердить конкретное списание остаётся
`action_required`; исполнитель не подменяет такое подтверждение.

Все четыре переключателя по умолчанию выключены:
`CRYPTO_STORE_CREATES_ENABLED`, `CRYPTO_LIVE_PURCHASES_ENABLED`,
`CRYPTO_ALLOW_UNIQUE_CENT_AMOUNTS`, `CRYPTO_EXCLUSIVE_POLLER_CONFIRMED`.
Их можно включать только после соответствующей настоящей проверки.

При последующем наличии уже оплаченного известного примера можно явно
задать `CRYPTO_STORE_BINDING_PROOF_FILE`. Его защищённый JSON содержит
`expectation` с полями `LicenseExpectation` и `source_path` существующего
исходного Device ID. Проверка читает соответствующие собственные записи
DriveMods и локальный файл, ничего не загружает в магазин и не создаёт
новую лицензию. В политике `strict` без такого доказательства приложение
не считается готовым.
Этот файл и исходный Device ID не включаются в ZIP или Git.

Альтернатива для первого реального заказа задаётся двумя явными настройками:
`CRYPTO_BINDING_POLICY=sha256_marker` и
`CRYPTO_ALLOW_FIRST_LIVE_VALIDATION=true`. Такая конфигурация разрешает
проверять привязку отдельно для каждого нового заказа. До списания должны
совпасть сохранённые магазином полные маркеры ID заказа и SHA-256 исходного
файла, владелец, новые ID записей, продукт, пакет, цена и единственная позиция
платежа. Пропавший или изменённый маркер блокирует оплату.

`binding_policy_configured=true` означает выбор этой политики, а не результат
проверки живого устройства. `real_device_flow_tested` остаётся `false`, пока
настоящая оплаченная цепочка не проверена. В runtime этот информационный
признак берётся из адаптера после проверки конкретного оплаченного заказа.
Старые записи журнала нельзя переинтерпретировать другой политикой.

## Будущий запуск после готовности

`--run` повторяет предварительную проверку и останавливается до создания
баз, если любое условие не выполнено. При полной готовности создаются
только новая `crypto-orders.sqlite3`, `store-journal.sqlite3`, папка
`uploads` и собственные lock/health файлы. Карточный `card-journal.sqlite3`
создаётся исполнителем только при фактическом запуске оплаты, до нажатия
платёжной кнопки. Далее собираются один worker
и один Telegram-поллер. Привязка заказа, точной суммы, перевода,
оплаченной лицензии и получателя проверяется соответствующими модулями.

CLI собирает только фиксированные локальные классы `OwnerCardVault` и
`BrowserStripeExecutor` при наличии соответствующих настроек. Явная передача
исполнителя из Python сохраняется для автономных тестов. Динамическая загрузка
класса по строке из `.env`, фиктивный результат оплаты и переключатель
«считать карту подключённой» не предусмотрены. Без успешной предварительной
проверки CLI `--run` остаётся заблокированным.

## Шаблон systemd, пока без установки и включения

Подготовлен `deploy/drivemods-checkout.service` с отдельным пользователем
`drivemods-checkout`, кодом `/opt/drivemods-checkout` и отдельной
`StateDirectory`. Он не содержит `Conflicts=`, остановки или перезапуска
действующей службы. `ExecCondition` сначала проверяет, что прежняя служба
`drivemods-license-bot.service` уже находится в `inactive` или `failed`.
После этого `application --run` внутри `ExecStart` выполняет полную проверку
и запуск пустого браузера до создания Ledger и Telegram poller.

Секреты предполагается передавать через `LoadCredential` systemd 247+:
защищённый `/etc/drivemods-checkout.env` и
`/etc/drivemods-checkout-session.json` копируются systemd в доступную
только службе папку credentials. В unit и Environment остаются только
пути и несекретные параметры. Для старой версии systemd потребуется
отдельно согласованная копия сессии с правами пользователя службы.
Не ослабляйте права файла до общего чтения.

Две необязательные строки `LoadCredential` для `owner-card.enc` и
`owner-card.key` в шаблоне закомментированы до разрешения и установки файлов
владельцем. После подключения приложение обнаруживает их в
`CREDENTIALS_DIRECTORY`; отсутствие файлов не мешает обычной проверке остальных
сервисов. На проверенном systemd 249 credentials доступны основному
`ExecStart`, но недоступны `ExecStartPre`. Поэтому отдельный предварительный
процесс не используется: те же обязательные проверки выполняются внутри
`--run`, до создания баз, приёма счетов и запуска poller.

Отдельный файл `/etc/drivemods-checkout.hosts` монтируется только для новой
службы поверх её `/etc/hosts` через `BindReadOnlyPaths`. Глобальный hosts
сервера не меняется; доменные имена HTTPS и проверка сертификатов сохраняются.
Этот файл предварительно готовит владелец сервера, иначе запуск службы
блокируется на подготовке окружения.

Для проверенной серверной версии systemd 249 unit использует переменную
`CREDENTIALS_DIRECTORY` через явный `/bin/sh -c`, затем `exec` запускает
Python. Обозначение `%d`, отсутствующее в этой версии systemd, не
используется. Двойные знаки доллара в unit передают переменную оболочке;
в ней находятся только пути к закрытым файлам, значения ключей не
подставляются в аргументы командной строки.

Обычная проверка кода не создаёт каталог данных. При явно запрошенной
попытке запуска systemd может подготовить только собственную новую
StateDirectory до проверки; это не перенос и не изменение прежней БД.

Прежде чем включать новый unit, нужно сохранить согласованную копию
прежнего состояния, завершить доказательства устройства и исполнения
платежа, проверить единственный poller и провести отдельно проверенное
переключение. Запуск unit не выполняется автоматически при сборке ZIP.
На другом компьютере нельзя запускать вторую копию с тем же рабочим
токеном. Шаблон не является доказательством, что полная автоматика уже
действует.

Проверки шаблона основаны на официальной документации
[systemd credentials](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)
и [ExecCondition](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html).

## Локальные проверки

```sh
python -m pytest tests/test_crypto_application.py -q
```

Тесты используют явно переданные автономные фабрики клиентов. Они
проверяют отсутствие записей при `--check`, закрытие соединений,
безопасные сообщения об ошибках, изоляцию каталогов и баз, отказ
неправильного токена/сети, выключенные флаги и сборку настоящих типов
только после прохождения всех проверок. Они не создают настоящую
лицензию и не списывают деньги.
