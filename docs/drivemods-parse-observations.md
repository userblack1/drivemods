# Чтение оплаченной лицензии DriveMods

`crypto_checkout.drivemods.DriveModsParseClient` принимает логин и пароль от вызывающего кода, читает только отдельные записи своего аккаунта и возвращает файл после строгой сверки. Он **не создаёт лицензии, счета или Stripe Checkout, не списывает деньги и сам ничего не запускает**. Доступы из браузера, `.env` и чужих сессий не извлекаются. Запись выполняет отдельный явно настроенный `DriveModsPurchaseClient` с защитами адаптера.

## Что подтверждено исходниками сайта

24 ноября 2026 года исследованы публичные ресурсы официального магазина: [главный JavaScript](https://store.drivemods.org/static/js/main.59c16fa9e1ab.js), [форма лицензий и оплаты](https://store.drivemods.org/static/js/742.6075bde0bf16.chunk.js), [Parse SDK сайта](https://store.drivemods.org/static/js/common_app.3e205cca23b2.js). Приложение целиком не запускалось; декодировались только изолированные функции строковых таблиц, затем анализировалось синтаксическое дерево. Рабочие реквизиты не читались, запросы к бизнес-функциям не выполнялись.

Это внутренний интерфейс веб-приложения, а не опубликованный DriveMods договор интеграции. Подтверждено наличие вызовов и полей в клиентском коде; реальные ответы и права конкретного аккаунта пока не проверены.

| Элемент | Наблюдение |
| --- | --- |
| Parse Server | `https://store.drivemods.org/parse/` |
| Application ID | `dmStoreApp`, публичный идентификатор приложения |
| JavaScript key | В конфигурации сайта пустой |
| Версия приложения | `1.3.3` |
| Авторизация | `Parse.User.logIn(username, password)` |
| Чтение | `processQuery({type:"GET_ONE", resource:"Record", params:{id}, appVersion})` |
| Ответ чтения | `result.data`, возможна сериализация Parse Object/Pointer |
| Типы записей | `2` — лицензия, `4` — её платёж |
| Статусы | `1` — не оплачен, `2` — оплачивается, `3` — оплачен, `4` — отменён |
| Валюта | `2` — USD; `1` — RUB; `3` — CNY |
| Принадлежность | `createdBy` — объект/указатель `_User` |
| Связь платежа | `payItems[]`: `id` исходной записи лицензии, `quantity`, `sum` |
| Файл | `licFile` декодируется локально; имя `licFileName` |

В поставляемом Parse SDK вызов Cloud.run использует `POST functions/<имя>`. Авторизация и идентификатор приложения передаются в JSON как `_SessionToken` и `_ApplicationId`; методы, отличные от POST, кодируются через `_method`. Реализованный клиент использует этот формат и фиксированный HTTPS-адрес, не следует перенаправлениям и не использует настройки прокси из окружения.

## Проверка конкретного заказа

`LicenseExpectation` должен создаваться из сохранённых привязок заказа, а не из сообщения клиента с номером чужой лицензии. Для FULL разрешена закупочная цена $90, для ECO — $60. Клиентская цена $100/$70 относится к отдельному платежу покупателя и здесь не подтверждается.

`reconcile_paid_license(expectation, source_bytes)` проверяет:

1. SHA-256 исходного Device ID и аккаунт, под которым выполнен вход.
2. Точные, различные `payment_id` и `license_id`, сохранённые в заказе.
3. Владельца обеих записей; типы `4` и `2`; `isActive=true`; `paymentStatus=3`; USD и точную цену пакета.
4. Единственную позицию платежа: требуемый ID лицензии, количество 1 и точную сумму. Дополнительные позиции, даже бесплатные, требуют отдельного разбора.
5. Точные `product`, `bundle` и `region` лицензии. По умолчанию обязательно точное поле `deviceId`; опционально проверяется комментарий обеих записей. Отдельная явно выбранная политика `sha256_marker` допускает отсутствующее поле `deviceId` только с обязательным полным `crypto-order:<invoice_id>:<source_sha256>` в обеих записях и теми же строгими проверками ID, владельца, цены и позиции. Другой присутствующий `deviceId` не допускается. Настройка этой политики не означает, что сквозной живой тест уже выполнен.
6. Каноническое стандартное Base64 с `=` или без завершающего padding, ограничение размера, безопасное имя файла и отсутствие типичного HTML, ошибки JSON, изображения, PDF или повторной выдачи исходного Device ID. Неполные/лишние padding и ненулевые отброшенные биты отклоняются.
7. SHA-256 выдаваемого файла; при повторном получении можно потребовать совпадение с ранее сохранённым `license_sha256`.

Файл возвращается в `VerifiedLicense.content`, хеш — в `.sha256`. Это сверка с записями поставщика и контроль неизменности файла. Криптографическая проверка подписи лицензии для конкретного ШГУ не реализована: её формат публичными ресурсами не установлен. Отклонение, неизвестная структура ответа или статус 2 завершаются ошибкой; они не разрешают повторную покупку.

Существование `licFile` и кнопки скачивания само по себе не подтверждает оплату: сайт показывает файл и до её завершения. Проверка статусов обеих записей намеренно обязательна.

## Минимальное использование после отдельной проверки доступов

```python
from getpass import getpass
from crypto_checkout.drivemods import DriveModsParseClient

async def inspect_existing_record(record_id: str):
    async with DriveModsParseClient() as client:
        await client.login(input("Логин DriveMods: "), getpass("Пароль DriveMods: "))
        return await client.get_owned_record(record_id)
```

Не печатайте реквизиты и полные ответы. Клиент удаляет сессию из своих полей при закрытии и перед повторным входом. `export_session()` явно возвращает `ParseSession(username,user_id,session_token)` с выключенным `repr`; пароль не сохраняется. `resume_session(session_token,user_id,username)` проверяет явно переданную сессию чтением `users/me` и сверяет точные имя и ID; при отказе очищает её. Экспорт сессии нужно хранить отдельно от исходников и защищать как пароль. Токен, пароль, файл и исходные ответы не входят в тексты исключений или `repr` результатов. Внешний HTTP debug-логгер с записью тел запросов подключать нельзя.

Проверка без сети: `python -m pytest tests/test_drivemods_parse.py -q`. Тесты используют только `httpx.MockTransport`; вход в настоящий аккаунт и покупка не выполняются.

## Что требуется до настоящей закупки

- С разрешённым входом проверить формат `GET_ONE Record` на существующих собственных записях: точную связь `payItems.id`, валюту, владельца, статусы и двоичное кодирование. Пока тесты проверяют контракт по публичному клиенту, а не подтверждённые ответы сервера.
- Проверить фактические значения `bundle` для FULL/ECO и текущие цены своего аккаунта. Публичный клиент получает `getUserPriceGroup({appVersion}).currency` и `getUserPriceItems({appVersion})`: элементы содержат `isActive`, `price`, `product` с полями `name`, `spec`, `region`. Библиотека сейчас допускает только пакет, равный FULL/ECO без иных слов; неизвестное название блокируется.
- Подтвердить ответ и привязку создаваемой лицензии к заказу. Наблюдаемая `createNewLicense` передаёт `rid`, `uid`, Base64url Device ID, продукт, пакет, регион, версию, `operationId`, цену, валюту и комментарий. `rid="RQ-"+UUID` не является доказанным ключом идемпотентности. После неопределённого таймаута нельзя повторять создание вслепую.
- Проверить создание ровно одного платёжного документа под нужную запись. В отдельном [guarded-адаптере](store-adapter.md) реализованы наблюдаемые вызовы создания с отключёнными по умолчанию флагами. Обычный `DriveModsParseClient` остаётся только для чтения. Реальные ответы создания и права аккаунта пока не проверены.
- Решить реальное списание Visa. В сайте `checkStripeOrder({id,payment_id,appVersion})` **создаёт/получает Checkout Session**, возвращает `client_secret` и открывает Stripe Embedded Checkout. Это не функция чтения статуса и не команда списания сохранённой карты без участия пользователя. Сохранение карты в Link не доказывает возможность автономной оплаты; возможны повторный вход и 3DS.
- После завершения Stripe сайт вызывает `setPaymentIsPaying`, затем перечитывает данные. Статус «оплачивается» и событие Checkout `onComplete` не должны подменять подтверждённый `paymentStatus=3`.

Автоматическая проверка поступления клиента в Binance и закупка у DriveMods — разные этапы. Этот модуль не меняет их состояния и не обходит существующее разрешение запуска реальных закупок.

## Живая проверка чтения 24 ноября 2026

После явного разрешённого входа проверены три собственные записи лицензий через `GET_ONE`: неоплаченная MB-S5WM FULL $90, оплаченная LG-GEN5 CUSTOM+RUS $60 и оплаченная MB-S5WM FULL $90. Владельцы, типы, суммы и статусы читаются. Во всех трёх ответах **отсутствуют** `deviceId`, `dealerComment` и `region`. Это не доказывает, что новые записи никогда не содержат таких полей, и не является постоянным запретом первого запуска по политике SHA-маркера. Новый заказ должен сам сохранить свой точный полный маркер в обоих документах до оплаты карты. Равная сумма/модель/версия не является заменой этой привязке; старые оплаченные записи нельзя выдавать новому устройству по совпадению цены. Без нового Device ID этот сквозной путь пока не проверялся.

`licFile` в этих ответах — стандартный Base64 без завершающих `=`, после декодирования по 4096 байт. Файлы не являются JSON/UTF-8, gzip или ZIP; распознаваемые текстовые поля устройства/пакета не обнаружены. Высокая энтропия согласуется с непрозрачным зашифрованным/подписанным контейнером, но это только вывод по структуре. Расшифровка и криптографическая привязка к исходному Device ID не установлены.

Чтение собственного `users/me` показало `paymentMethod=8`, `isActive=true`, `prepayCnt=0`. Это не подтверждает кредитный баланс или право автоматически выдавать неоплаченные лицензии. Проверка была только для чтения: новые лицензии, счета, Checkout и списания не создавались.
