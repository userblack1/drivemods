# Совместная разработка с двух ноутбуков

Рабочий репозиторий владельца — https://github.com/userblack1/drivemods. По указанию владельца он остаётся **публичным**. Для второго разработчика нужен доступ Collaborator на запись. Каждый использует свой GitHub-аккаунт, Git Credential Manager или SSH; PAT/пароли не помещать в remote URL и командные строки. Секреты, реальные настройки и данные пользователей запрещено публиковать.

Если репозиторий уже содержит файлы, сначала изучите его историю и структуру. Импортируйте подготовленный код отдельной новой веткой через PR/согласованный подкаталог; не заменяйте main, чужие файлы и историю. Не объединяйте несвязанные истории автоматически. Force push запрещён.

## Первый ноутбук и второй ноутбук

```powershell
git clone https://github.com/userblack1/drivemods.git
cd <ПАПКА>
git config user.name "Ваше имя"
git config user.email "Ваш GitHub noreply или рабочий email"
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.dev.lock
.\.venv\Scripts\python.exe scripts/setup_dev_env.py
```

Примеры env намеренно пустые, целиком копировать их не нужно. Для Telegram-тестов — отдельный бот и отдельные данные. Действующий токен и серверную Telethon-сессию на ноутбуках не запускать.

## Каждая задача

Проверьте git status; собственные незавершённые изменения сохраните коммитом в своей ветке или осознанным stash. Не делайте reset/clean поверх работы.

```powershell
git switch main
git pull --ff-only
git switch -c task/short-description
# Внесите изменения.
.\.venv\Scripts\python.exe -m pytest -q
git diff --check
git add <ЯВНЫЕ_ПУТИ>
git diff --cached --stat
# Просмотрите весь git diff --cached локально.
.\.venv\Scripts\python.exe scripts/handoff_audit.py --history
git commit -m "Describe the change"
.\.venv\Scripts\python.exe scripts/handoff_audit.py --history
git push -u origin task/short-description
```

Создайте Pull Request, опишите поведение и проверки. Второй разработчик проверяет diff и CI, затем merge. На другом ноутбуке снова switch main и pull --ff-only. Если основная ветка называется иначе, используйте её имя. При расхождении main разберите историю, не перезаписывайте удалённую ветку. Для актуализации рабочей ветки — fetch origin и обычный merge origin/main, разрешение конфликтов, повторные тесты.

Владелец включает защиту main: PR, одно ревью, обязательный CI Windows/Linux. Actions закреплены SHA, производственные секреты в CI не передаются, деплой не выполняется. Облачный CI подтвердится только после загрузки; локальные тесты не означают, что GitHub уже прошёл проверки.

## Что исключено и как проверять

Не коммитить реальные env, ключи, токены, QR с личными реквизитами, клиентские ID/лицензии, БД/WAL, Telegram-сессии, браузерные профили/cookie, SSH-доступ, логи, venv, кэши и резервные копии. .gitignore не исключает уже отслеживаемые файлы. scripts/handoff_audit.py --history проверяет индекс, текущие файлы и все доступные Git-объекты, включая недостижимые; выдаёт только пути/правила без значений. Детектор дополняет ручной просмотр. Для дополнительной проверки используйте Gitleaks с --redact.

Если секрет обнаружен — не push. Сохраните исходный репозиторий защищённо, сообщите владельцу путь/правило без значения и подготовьте чистый снимок в отдельном репозитории. Для уже опубликованного секрета нужна согласованная ротация. Историю существующего проекта не переписывать.

## ZIP, Git bundle и сервер

ZIP из git archive содержит исходники **без .git и истории**. Для обычной работы предпочтительны GitHub clone/pull. Дополнительный проверенный .bundle содержит новую безопасную историю: `git clone <ПУТЬ_К_BUNDLE> <НОВАЯ_ПАПКА>`. Затем настройте origin на URL владельца, сначала проверив удалённые ветки. Bootstrap-коммит явно подписан автоматическим автором подготовки; последующие коммиты — собственным именем разработчика.

GitHub не обновляет VPS автоматически. Выпуск выполняет ответственный оператор по HANDOFF с резервной копией и отдельным согласованием. Не запускайте deploy-скрипты для проверки установки ноутбука.
